# Gate: Production → Polish


**Required Artifacts:**
- [ ] The code root has active code organized into subsystems
- [ ] All core mechanics from GDD are implemented (cross-reference `design/gdd/` with the code root)
- [ ] Main gameplay path is playable end-to-end
- [ ] Test files exist under the engine's test root — `tests/unit/` and `tests/integration/` (Godot, Web, Custom), `Assets/Tests/EditMode/` and `Assets/Tests/PlayMode/` (Unity), `Source/<Module>/Private/Tests/` (Unreal) — covering Logic and Integration stories
- [ ] All Logic stories from this sprint have corresponding unit test files in the engine's unit-test location (`tests/unit/`, `Assets/Tests/EditMode/` or `Source/<Module>/Private/Tests/`)
- [ ] Smoke check has been run with a PASS or PASS WITH WARNINGS verdict — report exists in `production/qa/` (a `quick` run, labelled `(quick — …)`, does not count: it skipped the coverage scan)
- [ ] At least one QA plan exists in `production/qa/` (generated by `/qa-plan`) covering this sprint, the final production sprint, or this Production stage — run `/qa-plan` if missing (CONCERNS — advisory, not blocking)
- [ ] QA sign-off report exists in `production/qa/` (generated by `/team-qa`) with verdict APPROVED or APPROVED WITH CONDITIONS
- [ ] At least 3 distinct playtest sessions documented in `production/qa/playtests/`
- [ ] Playtest reports cover: new player experience, mid-game systems, and difficulty curve
- [ ] Fun hypothesis from Game Concept has been explicitly validated or revised

**Quality Checks:**
- [ ] Tests are passing (run test suite via Bash)
- [ ] No open S1 Critical bugs in any bug tracker or known issues
- [ ] Core loop plays as designed (compare to GDD acceptance criteria)
- [ ] Performance is within budget (check `performance.*` in `project.yaml`, else technical-preferences.md targets)
- [ ] Playtest findings have been reviewed and critical fun issues addressed (not just documented)
- [ ] No "confusion loops" identified — no point in the game where >50% of playtesters got stuck without knowing why
- [ ] Difficulty curve matches the Difficulty Curve design document (if one exists at `design/difficulty-curve.md`)
- [ ] All implemented screens have corresponding UX specs (no "designed in-code" screens)
- [ ] Interaction pattern library is up-to-date with all patterns used in implementation
- [ ] Accessibility compliance verified against committed tier in `design/accessibility-requirements.md`

## Workflow tier reductions

The checklist above is the **`full` baseline**. At lower tiers apply the
reduction for the resolved tier; items not named keep their status above.
Reductions only ever *relax* a requirement — `workflow_overrides` is the
only thing that adds one.

- **`full`** — core mechanics + Logic/Integration tests + smoke check (PASS or PASS WITH WARNINGS) + QA sign-off + 3+ playtests all required
- **`standard`** — QA sign-off + per-story test coverage → recommended;
  **core mechanics + smoke check + playable end-to-end + 1+ documented
  playtest + no open S1 Critical bugs** required
- **`minimal`** — **smoke check + playable end-to-end + no open S1 Critical
  bugs** required; the core-mechanics cross-check → recommended; everything
  else **drops**. Reductions relax what must *exist*, never what must *work* —
  a gate that closes production on "it boots" alone has not asked whether the
  game plays.

## Custom engine additions

**Applies only when the resolved `engine` line reads `Custom`** (any case). On
any other engine, or with no engine set, skip this block and print one line in
the report's checklist: `Custom engine additions: skipped — engine is <name |
unset>`. On Custom these items are added to the checklist above, and the frame
item is how "Performance is within budget" is checked for the engine.
Reviewer for this block: `chief-engine-architect`, through gate
**CEA-FRAME-BUDGET** on the newest capture against the baseline (Section 4b,
"Custom engine: chief-engine-architect").

**Quality Checks (Custom):**
- [ ] **Frame budget holds at P99 (CEA-FRAME-BUDGET).** The newest
      `/benchmark-report` in `production/qa/benchmarks/`, from an optimized build
      on the reference hardware, compared with the baseline: CPU frame P99 and GPU
      frame P99 at or under `performance.frame_budget_ms`, and CEA-FRAME-BUDGET
      returns APPROVE where the panel ran it.
      - `frame_budget_ms` unset, no report, a report whose verdict is
        `NOT ASSESSED`, a `CPU frame` or `GPU frame` row that reads
        `NOT ASSESSED`, or a `Regression result` line that reads `NOT ASSESSED`
        (this gate compares against the baseline, so it reads that line, not
        the verdict word) → NOT ASSESSED, with the reason. Never inferred from code
        or from an older capture of a different build
      - P99 (or P95) over budget, or a `REGRESSION` → a breach, handled by
        `performance.enforce` exactly as Section 3 says: CONCERNS at `warn`, a
        **Blocker** at `block`, informational at `off`. CEA-FRAME-BUDGET's own
        verdict is applied the same way (Section 4b)
- [ ] **Streaming and load-time targets measured.** Load-time targets (and,
      when the project has `engine/streaming/` or `engine/io/` or a streaming
      ADR, streaming targets: I/O bandwidth, streaming-pool budget, time to
      stream a cell in) are recorded in `frame-budget.md`, a module spec or an
      ADR, and each has a measurement. A target with no measurement, or no
      target recorded, is NOT ASSESSED for it. A measured miss is a breach,
      handled by `performance.enforce`.
- [ ] **Determinism replay tests, where determinism is claimed.** Derive the
      claims from the Accepted ADRs: each whose `## Determinism` section answers
      "yes" needs a replay test (same inputs, same seed → bit-identical state or
      checksum) under the test root that ran and passed in
      `bash .claude/scripts/test-run.sh custom`. A claim with no replay test is a
      **Blocker**; a section that reads `UNKNOWN` is NOT ASSESSED; no claim →
      the item reads `N/A — no ADR claims determinism`.

**Tier reductions (Custom).** Reductions only relax:
- **`full`** — every item above required
- **`standard`** — the frame-budget and determinism items required; streaming
  and load-time measurements → recommended
- **`minimal`** — the frame-budget item stays (Section 2b: the performance check
  runs at every tier and no reduction suppresses it); streaming, load-time and
  determinism items → recommended

A failing replay test is a test failure at every tier where it ran: Blocker or
CONCERNS by `testing.strict`, never dropped by a reduction.
